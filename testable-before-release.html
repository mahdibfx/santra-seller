What the customer chose on each item18 Octverified

lib/models/order_item.dart · lib/ui/views/order_detail/order_detail_view.dart · lib/ui/widgets/foldable_items.dart · test/order_dates_test.dart

What changed. The shop could not see the modifiers. An order for a cake with a size, a sponge and add-ons reached them as "Cake ×1", so they either made the wrong thing or phoned the customer. This was live.

The API has been sending them all along — checked against production on 18 Oct 2026: every item carries modifiers[] with both languages, the group name, price_addition and quantity. The app never read the field.

Now on the order page as one line per group, and inline in the board card's expanded item list. The GROUP is named as well as the option — "Chocolate" alone does not tell a baker whether that is the sponge, the filling or the drip.

How to test
  1. Open an order placed with options (orders 151457–151460 on production have one each).
  2. Under the item name: a bulleted line per group, e.g. Size: 10 inch.
  3. On the board, tap "show items" — the options appear under each item there too.
  4. An order whose items have NO options: nothing extra renders, no stray bullet or blank line.
  5. Switch to Arabic and check both screens: bullets on the right, Arabic comma (،) between options, no overflow.
  6. An item with several options from ONE group should read as a single line ("Add-ons: nuts، sprinkles"), not the group name repeated.
  7. An item with options from SEVERAL groups should keep one line each, in the order the customer was asked.
Pass: the shop can tell exactly what to make without opening anything else or calling the customer.
Known limit: on the board card the options are merged into one line without group names, because the card is tight. The order page carries the full breakdown. Say if the board should show groups too.
Still unused from the same payload: modifiers_price, unit_price, total_price, prep_time_minutes. All sent per item, none displayed — prep_time_minutes looks useful for planning a queue.

Delivery date and placed date on the order page13–14 Octneeds device

lib/models/order.dart · lib/ui/views/order_detail/order_detail_view.dart · assets/translations/{en,ar}.json

What changed. Shops could not see when an order is due or when it came in. The order page showed one line next to a calendar icon holding scheduled_slot_label — the delivery TYPE ("standard"), not a date. It now shows two labelled rows: Delivery (from delivery_date) and Placed (from created_at, exactly as the server sends it).

Why created_at and not received_at

received_at is when the SHOP got the order — for a card order, when the payment landed. The waiting timer counts from that. "Placed" means when the customer ordered, which is created_at. They differ by however long the customer took to pay.

How to test
  1. Open any order from the board.
  2. Under the order number, read the two rows.
  3. Check the Placed time matches what the backend holds for that order. The app does no timezone conversion.
  4. Open a PARCEL (order_kind: "delivery_service") and check both rows there too.
  5. Switch the app to Arabic and reopen.
Pass: both dates show, Placed is in local time, and the rows read right-to-left in Arabic.
Blocking on Ahmad: his interim currently stuffs the dates INTO scheduled_slot_label, which this page still renders as the window after the delivery date. If the interim is live when this ships, the line reads "Delivery: 15 Oct · 15 Oct · placed 13 Oct 14:05". He must withdraw the interim as this release goes out — he has already offered to. Afterwards it reads "Delivery: 15 Oct · 6:00 PM – 9:00 PM".
Delivery date on the board cards13 Octneeds device

lib/ui/widgets/order_card.dart

What changed. The board cards carried no date at all, so a shop planning the day had to open every order. Each card now shows BOTH the delivery date and the placed date under the chips.

One per line, not side by side: in Arabic both labels are longer than their English counterparts and ran out of width. The placed date is day-only here — the waiting timer above already carries the minutes, and the card has no room for a clock as well. Both screens share one formatter, so the order page and the card can never drift apart on timezone or format.

How to test
  1. Open the orders board with several orders on it.
  2. Each card should show a calendar line with the delivery date AND a clock line with the placed date.
  3. Check the placed date matches the backend's date for that order.
  4. Check a card for an order with no delivery date — the line should be ABSENT, not blank or wrong.
  5. Check a long shop/customer name does not push the date off the card.
  6. Switch to Arabic.
Pass: the date shows on cards that have one and is simply missing on those that do not.
